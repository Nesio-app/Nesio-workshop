# 财务账本 · 统一方案

> **一句话**：把「记账」做成账本（ledger）而不是列表——每笔是一条不可变的分录，
> 关联走双向 relations，聚合永远是算出来的，正确性靠**对账**证明而不是靠信任。
>
> 顺序不可颠倒：**地基 → 账本 → 对账 → 关联**。地基不可靠时，上面每一层都是错觉。

---

## 0. 为什么是这个顺序

四个 use case 问出了同一个坑（详见 `module-link-matrix.md`）：交易关联了人却只有财务页看得见、
小票不跟流水对账、机票邮件不建行程、发票不识别。合起来是一件事：
**关联的地基只覆盖记忆图内部，而一半业务对象不在图里。**

而账本要建在记忆图上，就必须先回答：这个图**存得住吗、同步得对吗**。
体检结果见下，有洞——所以地基排第一。

## 2. 会计原则映射（行业调研结论）

调研了 QuickBooks / Xero / Beancount / Plaid / YNAB 的实际做法。**核心结论是：
行业共识不是「不可改」，而是「改可以，但必须留痕，且对账状态要跟着变」。**

| 会计原则 | 行业做法 | 我们怎么落 |
|---|---|---|
| 账簿可审计 | QuickBooks **void（作废）优先于 delete**：金额归零、记录保留、审计日志留原值+操作人+时间 | 作废为主，物理删只给「刚录错还没同步」 |
| 改动留痕 | Xero 有 **Reconciliation History**，专看「谁在对账后改过已对账交易」 | 变更历史（改了什么、原值、何时） |
| 纠正过去靠新条目 | 传统会计：不修改过去，插入新分录抵消 | 退款/更正 = **新分录 + 关系**，原分录不动 |
| 校验靠断言 | Beancount **balance assertion**：断言某账户某日余额=X，算不上就报错；`pad` 把查不出的差额记到专门科目 | 断言 + 对账调整分录 |
| 收付实现制 | Plaid 给的是现金流 | 主账簿严格收付实现，永远跟银行对得上 |
| 资金流向 | 每笔说清从哪个账户进出 | 账户维度必填 → 余额可校验 |
| 分摊不改原账 | — | 分给某人是**分配维度**，原分录金额不变 |

### Plaid 的硬约束（查证）

**pending → posted 不是状态变更，是「删掉 pending + 新建 posted」**，新交易带
`pending_transaction_id`；会发 `TRANSACTIONS_REMOVED`。官方推荐 `/transactions/sync`。

我们的现状（`plaid/transactions/route.ts`）：
- ✅ 已用 `/transactions/sync` 游标增量（`:207`）
- ✅ 已处理 `removed`（`:222`）
- ✅ **pending 交易过滤不入库**（`:438`）→ 主账簿只记已入账，符合收付实现制

**Plaid 说 removed 时**：那是银行撤销，不是「从未发生」——走**作废**，不物理删。
否则用户会发现「昨天看到的一笔今天没了」且查不出为什么。

## 3. 三档冻结（取代「录入即冻结」）

| 档 | 什么状态 | 源字段（金额/日期/账户） | 人字段（分类/备注/关联/附件） |
|---|---|---|---|
| **① 未对账** | 刚录入，还没跟 statement 勾对 | **可改**，留变更历史 | 随便改 |
| **② 已对账** | 跟 statement 勾对过 / Plaid 已 posted | 改前须**先解除对账**，并警告「会让 X 月对账差 $Y」 | 随便改 |
| **③ 已锁定** | 期间已出报表 / 已报税 | **只能冲正** | 随便改 |

**源字段 / 人字段的划分是地基**：Plaid 会反复重同步，人字段永不被覆盖。
这不是新发明——`ingest-node.ts:120` 那条血泪注释（云 AI 富化把本地抽取字段整块抹掉，
导致「所有邮件都是今天」）就是没分层的后果。现在把它形式化。

## 4. 账目分录的形状

```
账目分录（LifeNode）
├─ 源字段（按档冻结）
│    金额 · 日期 · 商家 · 账户 · 方向 · 来源(plaid|manual|statement) · 外部 id
├─ 人字段（永不被同步覆盖）
│    分类 · 备注 · 标签 · txFlow · 对账状态
├─ assets：凭证（小票 / 发票 / 邮件截图 / statement 页）
└─ relations（双向）
     人 · 账户 · 行程 · 财物 · Tax · 商家 · 退款
```

**手工录入与 Plaid 完全同形**。差别只有源字段由谁首次写入。
关联能力、凭证能力、退款能力、对账能力**完全相同**。

### 退款

1. 退款是**独立分录**（它本来就是独立的银行事实）
2. 双向关系 `refunds` ↔ `refunded_by`，**允许一对多**（Amazon 一单多退）
3. **净额永远是算的**：`原支出 − Σ已关联退款`。原分录一个字不改
4. 配对走**建议 + 人确认**：同商户 + 金额 ≤ 原支出 + 之后 ≤90 天 + 方向相反；「不是」进否决记忆
5. 下游分两类：
   - **聚合类**（某人花销、月度支出、预算）→ 自动重算
   - **申报类**（Tax Record）→ **可见提示要求复核，不替用户改**

> 存净额才会「数字跳变」，存事实不会。这一条同时治了 QA #21。

## 5. 对账：一个概念统一四种场景

| 你提供的 | 断言的是 | 系统算的 |
|---|---|---|
| 银行 statement | 某账户 · 某日 · 期末余额 | 该账户到那天的分录累加 |
| 信用卡月结单 | 某卡 · 某月 · 消费合计 | 该卡该月分录合计 |
| 年终报告 / 1099 | 某类别 · 某年 · 合计 | 该类别该年合计 |
| 税单 | 某科目 · 某年 · 合计 | 该科目该年合计 |

```
① 输入断言（余额/合计 + 截止日）
② 系统算差额
③ 差额 = 0 → 打「已对账」标记，锁定该期间
④ 差额 ≠ 0 → 列出未达账项：
      · 只在银行有 → 我漏记了（一键补录）
      · 只在我账上有 → 重复/记错（去作废或改）
⑤ 差额小且查不出 → 记一笔可见的「对账调整」分录
      （beancount pad 思路：留痕，不掩盖，不假装平了）
```

**第 ⑤ 条是诚实设计的红线：查不出的差额不许自动抹平。**

## 6. Statement PDF 解析（现在就做）

### 设计原则

> **解析器永远不直接写账。它只产出「候选行」，进对账台，由你确认。**

理由：银行 PDF 版式千变万化，解析必然有错。错了不能污染账本——只能停在候选区。
这也让「发现逻辑问题立刻改」成立：重新解析同一个文件，候选重算，账本不受影响。

### 三层结构

```
① 取文本层（零 OCR）
   pdf.js（pdfjs-dist）在**浏览器端**抽 text items（含 x/y 坐标）
   → 绝大多数银行 statement 是文本型 PDF，不需要 OCR
   → 文件不出设备（隐私红线：statement 是最敏感的文件之一）

② 版式无关的行重建
   按 y 坐标聚成行（容差 ±2pt）→ 按 x 排序 → 得到「视觉行」
   这一步让解析器不依赖具体银行的列宽

③ 确定性抽取（正则 + 结构，零 AI）
   每行找：日期 | 描述 | 金额（可能有借/贷两列）
   - 日期：多格式（MM/DD、MM/DD/YYYY、YYYY-MM-DD、DD MMM YYYY）
   - 金额：$1,234.56 / (1,234.56) 括号负数 / 尾随 CR/DR
   - 方向：看列位置 + 括号 + CR/DR + 该账户类型（信用卡 vs 借记）
   同时抽**页眉锚点**：账户尾号、statement 期间、期初/期末余额
```

### 为什么零 AI

- **可复现**：同一个文件永远解析出同样结果，改了规则能立刻验证
- **可解释**：每个候选行能指回「PDF 第几页第几行」
- **免费**：符合「免费 = 端上/确定性」的产品红线
- **隐私**：statement 不出设备

AI 只在一个地方可选介入：**版式识别失败时**给出「这张表的列大概是什么」的建议，
且必须走付费云门 + 用户显式点「让 AI 试试」。默认路径永远是确定性的。

### 自校验（解析器自己知道自己对不对）

解析出来立刻做三个断言，这是 PDF 解析最关键的设计：

```
A. 期初余额 + Σ(解析出的交易) = 期末余额 ?
B. 解析出的交易日期是否都落在 statement 期间内 ?
C. 交易笔数 vs 页面上写的「N transactions」(若有) ?
```

**A 不成立 = 解析漏了或多了**，而不是把错的东西塞进账本。这比任何「置信度分数」都硬。

### 差额诊断：不许只报「差 $X」

报一个差额然后让人自己去翻 PDF，等于没做。诊断必须走完四步，**停在「等你点确认」**：

| 步 | 输出 | 例 |
|---|---|---|
| **① 哪里错** | 定位到**具体行**（PDF 第几页第几行 + 原始文本） | 「第 3 页第 17 行：`07/12 AMAZON MKTPL*2K4LM 1,234.56`」 |
| **② 为什么** | 命中的具体规则失败 | 「金额列解析成 `1` —— 这一行的千分位逗号被当成了列分隔」 |
| **③ 去哪查** | 一键跳到 PDF 那一页并高亮该行；同时给账本里的疑似对应项 | 「你账上 07/12 有一笔 AMAZON $12.34，日期吻合、金额不吻合」 |
| **④ 怎么改** | **已经算好的具体改法**，只等确认 | 「把这行金额读成 **$1,234.56** → 差额从 $1,222.22 变成 **$0.00**」 |

处置永远是两颗按钮：**「就这么改」/「不对，我自己来」**。
「不对」进否决记忆（同 `receipt-match` 的否决对），同一张单再解析不会重复建议。

**能给出 ④ 的判据**：差额 $D 与某个候选修正**完全相等**时才提议。
- 差额恰好等于某行「疑似漏读金额」→ 提议按该值读
- 差额恰好等于某笔账本已有交易的金额 → 提议「这笔重复了，作废其中一条」
- 差额恰好等于两笔之和 → 列出这两笔
- **凑不出精确解就不提议**，只报 ①②③ 并让用户手动处理。宁可少提议，不许瞎猜。

同一套诊断复用于年终报告 / 税单对不上（只是断言对象不同）。

### 落地形态

```
财务 → 对账 → 上传 statement
  ↓
解析 → 自校验 → 候选行列表（每行标：新增 / 已有匹配 / 冲突）
  ↓
逐行确认（或「全部接受匹配项」）
  ↓
写入账本 + 期末余额断言 → 差额为 0 → 锁定该期间
```

原始 PDF 作为**凭证**存 `local-file-store`，挂在该次对账记录上。

### 分阶段

| 阶段 | 内容 |
|---|---|
| **S1** | pdf.js 文本层 + 行重建 + 通用正则抽取 + 三条自校验 + 候选台 UI |
| **S2** | 按银行加「版式提示」（列位置/日期格式），只是加速，不是必需 |
| **S3** | CSV 导入（银行都能导，比 PDF 简单，覆盖 PDF 解析失败的兜底） |
| **S4** | 扫描件 OCR（图片型 PDF）——**最后做**，识别风险最高 |
